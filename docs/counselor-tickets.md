# 상담사 민원 → 부서별 KB → 티켓 답글

2026-09-22 로컬 구현. 공개 사이트에 배포한 상태는 아니다.

## 사용자 흐름

1. 시작하기의 ‘고장 민원 접수하기’에서 충전기 ID 또는 주소를 입력한다. 같은 번호가 여러 충전소에 있으면 위치를 대조해 직접 선택한다.
2. 운영사·용량·급속/완속·커넥터·위치를 읽고 필요한 표시 항목을 선택한다. 주변 조회는 같은 충전소의 다른 장비와 주소가 같은 도로인 충전소 후보를 반환한다.
3. ‘이 장비로 민원 접수’를 누르면 검색 결과를 접고, 선택 대상이 표시된 민원 양식으로 이동한다. 증상 입력란에 포커스가 놓인다.
4. 고객 진술과 확인한 시각·오류를 입력하고 앱개발팀, 충전기개발팀 또는 양쪽을 선택한다. 모르는 정보는 미확인으로 남는다.
5. 전달 내용을 미리 본 뒤 티켓을 보낸다. 서버는 선택한 DB 행과 KB를 다시 대조하고, 접수 당시 정보·문서 버전을 보관한다.
6. 수신 부서 화면에서 같은 티켓과 자기 부서의 KB를 읽는다. 참고한 항목, 확인 결과, 수행한 조치, 고객 안내 문구, 다음 행동을 기록해 상담사에게 회신한다.
7. 상담사는 티켓의 부서별 답글을 읽고 추가 정보를 회신할 수 있다. 모든 수신 부서가 확인 결과를 회신한 뒤 상담 종료가 가능하다.

## 단일 KB 원본

API 저장소의 `services/api/app/modules/knowhow/fixtures/support-kb-v1.json`:

- CS-001 v1: 상담사의 대상 확인, DB 정보 해석, 대체 장비, 전달 기준, 접수 양식과 회신 확인.
- APP-001 v1: 앱 대상 식별, 요청·응답 점검, 앱과 장비의 경계, 상담사 회신.
- DEVICE-001 v1: 장비 식별, 통신·이벤트 점검, 추가 점검·현장 담당 확인, 상담사 회신.

모두 시연용 업무 기준이며 실제 부서 승인 문서로 표시하지 않는다. UI는 KB 사본을 내장하지 않고 API에서 읽는다. `window.KnowHowSupport.readKnowledge()`는 같은 체험 세션을 재사용하여 원문 배열을 반환한다. 별도 데이터 리니지 화면도 이 인터페이스를 사용한다.

## 검증

실제 FastAPI와 격리된 전체 공개 스냅샷 DB로 브라우저에서 GS타워 주소 조회 → 200kW 급속 장비 선택 → 양쪽 부서 접수 → APP-001 근거의 추가 정보 요청 → DEVICE-001 근거의 점검 안내 답글을 실행했다. 티켓 KH-C5DCCD24에 서로 다른 두 부서 답글이 보존되었다. 입력·답글은 모두 시연임을 명시했다. 실제 장비 조작, 직원 메시지, 모델·임베딩 요청은 수행하지 않았다.

사용자 발견 사항: 장비 선택 후 양식은 생겼지만 화면 이동이 렌더보다 먼저 실행되어 버튼이 무반응처럼 보였다. 렌더 종료 후 이동·포커스로 고쳤고 실제 클릭 후 양식과 입력 포커스를 확인했다.

서버 자동 검사 10건: DB 사실·ID 중복, 원본 행 소속, 같은 도로 필터, KB 출처, 미확인 정보 보존, 두 부서 답글, 중복 요청, 동시 수정, 세션 분리·만료, 부서 권한, HTTP 경로·입력 한도·DB 준비 실패. UI 기존 AI 상태 27개 조합과 범용/데이터 흐름 검사, 빌드 설정 3건도 통과했다.

## 범위

- 실제 수집한 환경부 DB의 보존 자료를 읽는다. 사내 앱/장비 운영 DB와 실시간 로그는 아직 연결되지 않았다.
- 좌표가 없어 반경 검색·거리순 추천은 제공하지 않는다. 같은 도로의 주소 경계를 검사하며 충전소 이름에 도로명이 포함된 다른 주소는 제외한다.
- 공개 체험 역할은 실제 직원 인증이 아니다. 같은 8시간 체험 공간에서 세 역할을 전환한다. 운영 계정용 API는 별도 인증·배정 부서를 검사한다.
- 티켓과 답글은 서버 SQLite에 저장한다. 체험 세션은 8시간이며 새 세션으로 이전 티켓을 읽을 수 없다.
